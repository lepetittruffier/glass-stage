Measured on top of 835440ecaa with the `default` skin on a light terminal (`_LIGHT_MODE_CACHE` forced on). The wrapper returns the overlay value as authored. The downstream paths then run the light remap again on whatever `get_color` returned, so one key renders in two colors:

| path | `banner_dim` (authored `#B8860B` in `light_colors`) |
|---|---|
| `get_color`, banner panel (Rich) | `#B8860B` |
| streamed ANSI (`_SkinAwareAnsi` → `_hex_to_ansi`) | `#5C4500` |
| prompt hint / placeholder (`_build_tui_style_dict`) | `#5C4500` |

The two response boxes follow the same pattern: they wrap `get_color` in `_maybe_remap_for_light_mode`.

On `main` the second pass was harmless, because no remap output is itself a key. With overlays, an authored value that happens to be a table key (`#B8860B`, `#F5F5F5`, …) is rewritten on some paths and kept on others.

This also bears on @lijiek's precedence point. Whichever order lands, it can be decided once, in the wrapper, if the downstream paths stop re-running the remap:

- `_hex_to_ansi` takes `remap=False` for values `get_color` already resolved (`_SkinAwareAnsi`).
- `_build_tui_style_dict` remaps the base styles first, then layers `get_prompt_toolkit_style_overrides()` on top, already resolved.
- The response boxes in `cli_commands_mixin.py` and `cli_chat_turn_mixin.py` take `get_color` as-is.

Applied on top of this branch, `test_cli_light_mode.py` and `test_skin_palettes.py` go from 48 to 50 passed (2 skipped). The two new tests pin the behavior: an authored `#FFD700` stays `#FFD700` in the hint style and in ANSI, and an unpaired `#FFD700` is remapped exactly once, to `#9A6B00`. All four paths above then read `#B8860B`, and ruff is clean.

Related: #107175 builds the painted-surface styles from `skin.colors.get(...)` directly, which skips this wrapper and so skips the overlays. On a light terminal, those surfaces would keep the base fills instead of `light_colors`' light ones (`default`'s `status_bar_bg: #F5F5F5`, for example). One resolution point would let the two PRs agree.
